# 桌面语音输入重复修复（2026-11-06）

## 目标与范围

用户在豆包输入法升级到 1.0.3 后仍遇到文字重复，示例为“优化选择的心态”。第一轮只验证
YahaDesk 固件的 Wi-Fi 实时性候选；用户烧录后复验仍重复，第二个例子为“现在好像还是有问题。
现在好像是有问题”。第二轮回到上午稳定基线，检查固件采音生命周期；不改 BLE/Opus 协议、
Mac 120 ms 缓冲、BlackHole 格式与当晚在途 UI。新候选固件未获得再次烧录授权。

## 诊断与决策证据

- 20 秒受控负载中设备采集间隔保持 `59/59/60 ms`；345 个音频包全部接收、解码、入队，
  丢包、溢出和新增欠载均为 0。没有证据表明今晚 UI 改动抢占了 I2S 采集。
- 当前固件启动日志明确出现 `wifi:pm start, type: 1`，即 ESP-IDF 默认的
  `WIFI_PS_MIN_MODEM` 正在生效。
- 2026-11-01 的旧 yahamic 记录写明：其 Wi-Fi UDP 音频链路曾因默认省电出现周期性卡顿，
  当时使用 `esp_wifi_set_ps(WIFI_PS_NONE)`。当前 YahaDesk 音频走 BLE，这条历史只能提供候选方向，
  不能直接证明本次根因。
- Espressif 官方文档确认默认模式是 `WIFI_PS_MIN_MODEM`，关闭 modem-sleep 会增加功耗，
  但能把 Wi-Fi 实时接收延迟降到最低。xiaozhi-esp32 则把音频输入放在独立高优先级任务；本项目现有
  采集任务也已独立为优先级 6、Core 1，本轮不重复改任务模型。

## 实现与兼容

- 作为最小可回滚实验，`cloud::initialize()` 在 `esp_wifi_init()` 和 station 模式配置后调用
  `esp_wifi_set_ps(WIFI_PS_NONE)`；失败沿用现有 `wifi_init_failed` 路径，不带病启动。
- 保持 Mac 120 ms 缓冲基线不变，便于比较候选策略效果，不额外增加 60 ms 首字延迟。
- 不改 UI、任务绑核、协议和持久化格式。代码回滚即可恢复旧行为；代价是设备联网期间功耗上升。

## 第二轮：codec 保温回归

### 新证据

- 用户在第一轮固件生效后真人复验仍得到两句近义重复，证明 `WIFI_PS_NONE` 没有解决文字问题；
  它只保留为已验证生效的无线共存性能策略。
- 23:38 的两次 Fn 会话里，BLE 收包、Opus 解码、抖动缓冲入队和 BlackHole 输出累计始终一致，
  `rxInvalid/decodeErrors/dropJump/overflows` 均为 0。短会话各出现的欠载计数来自 `beginStream()`
  先于首帧入队的统计竞态；不能据此认定话中断流。
- 受控播放“现在好像还是有问题”时，同时录制解码后的 16 kHz PCM 与 BlackHole 48 kHz PCM。
  BlackHole 只有一个完整语音段（约 3.153–5.015 秒），没有整句 PCM 重播，也没有新增欠载；
  句前和句后各有一个极短脉冲（约 20 ms 与 6 ms）。该证据只能排除这轮的整句 PCM 重播，
  不能证明重复一定发生在哪个听写内部阶段；边界脉冲是否触发下游重复也仍待 A/B 验证。
- Git 历史显示，用户所说的晚间 UI 提交只改显示。上午稳定基线之后唯一改变采音生命周期的是
  `a21468ea`（15:57）：静音后 ES7210 继续读帧保温 30 秒。该优化把热开麦延迟从
  143–151 ms 降到 86–116 ms，但改变了每次讲话的物理开关边界，且当日真人文字回归未通过。

### 决策与实现

- 最小回滚 `a21468ea` 的 codec 保温部分：保留约 240 ms 的静音淡出，淡出结束后立即关闭 codec；
  下次开麦继续丢弃上电瞬态首帧。UI、Wi-Fi 性能档、BLE 协议和 Mac 缓冲均不变。
- 接受恢复冷开麦约 0.1 秒延迟的取舍；用户说话前需留极短起音余量。先恢复已知稳定行为，
  不新增可配置保温时间或另一套会话状态机。
- 新增 `audio_mute_lifecycle_test.py`，编译执行真实 `capture_loop()` 静音分支。当前保温版本先失败；
  回滚后验证淡出结束关 codec 且静音期不再读帧，同时末个淡出帧仍保持 codec 打开。独立审查
  发现回滚曾误删单次静音快照，构造 `load(false)` 后并发发布静音的交错可让 codec 抢先关闭；
  已恢复同一轮单次快照，并补充会在故障版本失败的确定性回归。

## 第三轮：先建立音频质量闭环

用户要求先做完整压力测试、逐轮对比与降噪/增强，再判断文字层；随后提出在 Mac App 录制本人语音、
备份到网盘，并用本地模型增强本人声音、过滤其他说话人。该方向与文字重复修复分开验证，暂不把模型
接入正式 BlackHole 输出。

### 现状基线（当前已烧录的 Wi-Fi 候选，不含上述 codec 回滚）

- 60 秒连续 TTS + 解码 PCM/BlackHole 并行录音：完整帧、解码、入队均为 1043，
  `rxInvalid/decodeErrors/dropJump/overflows` 为 0，但 BlackHole 渲染欠载新增 5 次，最低 7 帧/秒。
- 排除录音抽头影响后再跑 60 秒纯指标对照：完整帧、解码、入队均为 1040，同样零错零丢，
  BlackHole 渲染欠载仍新增 4 次，最低 10 帧/秒。故欠载不是诊断录音造成，必须先于降噪处理。
- 解码 PCM 的整段统计为 RMS -35.79 dBFS、噪声底约 -57.24 dBFS，并有 3 个孤立满幅样本；
  固件当前 ES7210 增益为上限 37.5 dB。TTS 扬声器回录不能代替真人近讲/远讲/环境噪声样本，
  这些数字只作为本轮相对基线，不据此直接下调增益或选择模型。

### 算法边界与推荐顺序

1. 先把连续 60 秒渲染欠载收敛到 0，并让压力工具同时保存解码 PCM、最终 BlackHole 与分阶段时序；
   不允许诊断抽头改变实时结果。
2. 普通噪声/混响增强在 Mac 端离线 A/B 后再实时化。RNNoise/LocalVQE 一类只能处理噪声、混响或
   回声，不能按身份过滤另一位说话人；接入前要验证本人可懂度没有因过抑制下降。
3. 本人声纹先做“录制 → 质量门禁 → 本地 embedding → 明确授权后备份原始样本 → 可删除/重录”。
   embedding 只用于本地比对，网盘原声不应成为每次说话的在线依赖。
4. 声纹门控只能抑制非重叠的他人语段；本人和他人同时说话需要目标说话人提取（TSE）模型。
   Google VoiceFilter-Lite 没有公开可直接集成的正式模型且输出面向 ASR 特征；WeSep 当前仍标明
   生产部署与预训练模型未就绪。因此先做门控 MVP，重叠语音分离作为独立训练/模型交付批次。

### 待用户决策

- 推荐先交付 P0（欠载归零 + 三段音频对比工具）和 P1（5 句本人录音、网盘备份、本地声纹门控、
  普通降噪离线 A/B），明确验收后再决定是否投入 P2 的重叠人声提取模型训练与 Core ML 转换。
- 隐私边界需在实现前确认：本人原声默认上传网盘还是仅用户点“备份”后上传；删除声纹时是否同时
  删除网盘原声。实际上传/删除属于生产数据动作，逐次由用户操作或单独授权。
